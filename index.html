02 case studies
01
Collection tooling · source reviewed

A filename assumption weakened a transient-file investigation.

During analysis of a Windows executable, a file collector produced no matching captures. Review of the collection logic identified filename restrictions that could exclude relevant temporary files before their contents were examined.

What the investigation found

The earlier collector rejected names shorter than 16 characters and files with extensions. The investigation record identified a 13-character temporary filename that was skipped. That meant an empty capture directory could not establish that no relevant file had appeared.

What changed

The filename restrictions were removed. The current collector selects files by a fixed set of byte lengths, computes SHA-256 hashes, avoids duplicate captures, and writes snapshots with a quarantine filename extension. That extension is a naming convention, not an operating-system security boundary.

Documented outcomeThe investigation record reports a successful rebuild and restart. The source inspected for this portfolio confirms that filename length and extension no longer determine eligibility.

Source corroboration

The reviewed C# source uses FileSystemWatcher for create, change, and rename events. Capture selection checks ExactSizes.Contains(size); deduplication uses size plus SHA-256. The basename is used when naming the saved snapshot.

Limits: No fresh runtime reproduction was performed for this publication. Size filtering, event delivery, files outside the watched directory, and rapid deletion can still prevent collection. This is a tooling-reliability finding; it does not establish malicious behavior or a vulnerability in the analyzed executable.

02
Kernel crash triage · preliminary review

Separating a Windows crash hypothesis from demonstrated defects.

A review of reconstructed Windows driver code examined a proposed copy-on-write explanation for a system crash. The review distinguished the reported crash classification from assumptions about the root cause and identified cleanup and execution-context questions.

Diagnostic reasoning

The supplied account described bug check 0x1E as a double fault. Microsoft documents 0x1E as an unhandled kernel-mode exception; a double fault is associated with 0x7F and first parameter 8. The review requested the exception details and crash stack before accepting a root-cause claim.

Code-review observations

The reconstructed exception path appeared able to free an MDL after a successful page lock without the corresponding unlock if a later operation failed. The review also raised questions about pointer validity across process attachment and whether the caller met the documented IRQL requirements.

Documented outcomeThe review produced a focused diagnostic next step: obtain the crash dump, exception parameters, and stack, then check resource cleanup and address-space assumptions against the actual failing path.

Limits: The reviewed code was reconstructed. No crash dump, validated reproduction, confirmed exploitability, completed fix, or vendor acknowledgment is established by this case study. The observations remain preliminary code-review findings.

Research approach

Make each conclusion traceable.

The emphasis is on careful software analysis and reliable evidence, with uncertainty retained where the record is incomplete.

  1. Inspect the available artifact.Review code, binaries, diagnostic logs, and the tools used to obtain them. Check whether the evidence collector itself could explain a missing result.
  2. Separate observations from explanations.A crash report, a review hypothesis, and a reproduced security flaw carry different levels of confidence.
  3. Check platform contracts.Compare resource lifetime, process context, and execution requirements with primary platform documentation.
  4. Record what remains unresolved.Keep reproduction gaps, missing artifacts, and unverified impact visible in the written result.

CASE 1: TRANSIENT-FILE COLLECTOR RELIABILITY
An earlier file collector excluded filenames shorter than 16 characters and files with extensions. The investigation record identified a skipped 13-character temporary filename. Empty output was therefore insufficient evidence that relevant files had not appeared.

The filename restrictions were removed. The current C# source was inspected while preparing this publication. It selects candidates by fixed byte lengths, computes SHA-256 hashes, deduplicates by size and hash, and writes snapshots using a quarantine filename extension. That extension is a naming convention, not an operating-system security boundary. The record reports a successful rebuild and restart.

Limitations: No new runtime reproduction was performed for this portfolio. Files can still be missed through size mismatch, event-delivery limits, deletion races, or location outside the watched directory. The finding concerns collection reliability; it does not establish malicious behavior or a security flaw in the analyzed executable.

CASE 2: RECONSTRUCTED WINDOWS DRIVER CRASH REVIEW
A review challenged an unsupported explanation of bug check 0x1E as a double fault. Microsoft documents 0x1E as an unhandled kernel-mode exception; a double fault is associated with 0x7F and first parameter 8.

The review also identified an apparent exception-path cleanup problem in reconstructed code: a successful page lock might not be paired with an unlock before an MDL was freed after a later failure. Pointer validity across process attachment and caller IRQL remained open questions. The next diagnostic step was to obtain crash-dump parameters and the failing stack.

Limitations: Reconstructed code, no crash dump, no validated reproduction, no confirmed exploitability, no completed remediation, and no vendor acknowledgment established. These are preliminary code-review findings.
